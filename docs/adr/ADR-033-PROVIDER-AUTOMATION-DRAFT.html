ADR 033 (DRAFT — awaiting user confirmation) — Dynamic LLM Provider Routing Automation

Status: DRAFT v2 — revised with user feedback 2026-09-27 (p95 latency, throughput, 3-component price, dynamic candidate set + two-step allowlist, auto-mode-first). Awaiting explicit confirmation.

Context

The OC model standard pins GLM-5.3-flash to a sticky provider order (Morph → Together → CoreWeave → Relace, allow_fallbacks: false) via the OpenRouter preset @preset/glm-53-flash-on-cheap. The provider landscape is highly dynamic: Relace (2 days ago) → CoreWeave (yesterday) → Morph (today) → tomorrow unknown. Morph's failover to Together was the preset working as designed (sticky failover after Morph rate-limited), but nothing fails back to Morph when it recovers, and nothing alerts when the first-choice provider degrades. Client config can never drift from the pin (preset is enforced gateway-side, verified 2026-09-27), so the automation target is the preset itself, not opencode.json.

Decision (proposed)

A scheduled checker (Vercel Cron, 1×/hour, well under the existing cron budget) that:

#StepDetail
1MeasureQuery OpenRouter for glm-5.3-flash endpoint health per provider over the trailing 24h: p95 latency, p95 throughput (tps), uptime, and the three price components — input, output, cache-read (cache-read weighted most: a sticky provider serves mostly cache hits, so cache price is the real cost driver). Plus a synthetic 1-token probe per candidate (cost ≈ $0.0001/probe). Empirical anchors (user-provided, 2026-09-27): Morph p95-latency ~3s vs Together 5.68s vs Relace 8.13s; throughput ≥50 tps acceptable, higher better; cache-read $0.032/M (Morph) vs $0.05 (CoreWeave) vs $0.03 (Together) vs $0.02 (Relace); input/output $0.16/$0.57 (Morph) vs ~$0.15/$0.50 (others).
2DecideScore the candidate set (uptime ≥99% first, then p95 latency, then p95 throughput, then the 3-component price weighted cache-read > input ≈ output). The candidate set is NOT frozen at the pinned four: if a provider outside the current set is doing better, it is recommended but flagged — activating it is a two-step process (add it in OpenRouter privacy settings FIRST, then add to the order; reordering alone leaves it unavailable, the exact Morph-onboarding lesson of 2026-09-27).
3Act (two modes)Auto mode (user preference, starts immediately): PATCH the preset via OpenRouter's presets API when the new order differs from the current one, with a minimum change interval (24h) and a full audit log; every automatic decision is also surfaced as an alert on the admin dashboard so the user can audit it. Alert-only mode remains available via provider.automation.mode = alert. Run in auto+alerts for 2-3 days; if decisions are wrong, tune the scoring algorithm with the recorded evidence.
4GuardrailsNever auto-activates a provider that is not in the OpenRouter privacy allowlist — it recommends the two-step activation instead. Order changes are confined to already-allowlisted providers. Never disables allow_fallbacks: false. Settings-Registry-gated (provider.automation.enabled, default true after confirmation; provider.automation.mode = auto|alert, default auto). No hardcoded tunables.

Alternatives considered

OptionWhy not (or why deferred)
Do nothing (manual preset edits)Current state. Works but drift is invisible until the user notices a slow/expensive provider.
OpenRouter "sort by latency/price" dynamic routingDefeats sticky-provider cache retention (the original reason for allow_fallbacks:false) — provider hopping per request loses the prompt cache.
Auto-update on every degrade (no min interval)Order flapping would thrash caches; 24h min interval mitigates.

Rationale

Preserves the confirmed sticky-provider design while removing the manual re-pinning chore. Alert-mode first (zero risk); auto-mode is opt-in behind a Settings key the user controls.

Cost

~24 probe requests/day ≈ $0.0024/day ≈ $0.07/month, plus cron invocation cost. Alert-mode only writes dashboard lines; auto-mode adds PATCH calls (free).
