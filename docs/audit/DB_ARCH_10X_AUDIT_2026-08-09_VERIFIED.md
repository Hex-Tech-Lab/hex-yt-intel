## ⚡ HIGH

### H1. `usage_logs_action_check` re-creation migrations have no `IF EXISTS` / `NOT VALID`

- **Files**: `supabase/migrations/20260802122006_usage_logs_action_check_add_dimension_remediation.sql:13`, `supabase/migrations/20260802144212_usage_logs_action_check_add_report_download.sql:14`
- **Finding**: Both migrations run `alter table public.usage_logs drop constraint usage_logs_action_check;` (no `if exists`) then `add constraint ... check (...)` with no `not valid`.
  - Missing `if exists`: a retried/replayed migration run errors out instead of no-op'ing.
  - Missing `not valid`: `ADD CONSTRAINT ... CHECK` without `NOT VALID` takes an `ACCESS EXCLUSIVE` lock and validates every existing row before releasing it — on a table this size (204 rows today) the practical blocking window is trivial, but the pattern is unsafe if `usage_logs` grows (it has an active daily purge job keeping it small — see L1 below — which is the only reason this hasn't bitten yet).
- **Verification method**: Read both migration files directly (full contents shown above); cross-checked the resulting live constraint via `execute_sql`: `SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid='public.usage_logs'::regclass` returned `usage_logs_action_check` with all 19 action values present (correctly merged both migrations), confirming the migrations did apply as written.
- **Current risk**: Low-probability today (small table, no evidence a migration replay has ever hit this), but the pattern is real and would bite on `usage_logs` growth or a future `DROP CONSTRAINT` typo/retry. Any future ALTER on this constraint should use:
  ```sql
  ALTER TABLE public.usage_logs DROP CONSTRAINT IF EXISTS usage_logs_action_check;
  ALTER TABLE public.usage_logs ADD CONSTRAINT usage_logs_action_check CHECK (...) NOT VALID;
  ALTER TABLE public.usage_logs VALIDATE CONSTRAINT usage_logs_action_check;
  ```
- **Not fixing live**: this is a read-only audit; no migration was applied.

## 🛡️ MEDIUM

### M1. Three `SECURITY DEFINER` functions callable by `anon`/`authenticated` without an explicit `REVOKE`

- **Verification method**: `get_advisors(type=security)` live output (saved in full to a tool-results file due to size; the relevant lint entries were read directly from the tool response).
- **Finding**:
  - `public.compliance_check_transcripts()` — executable by `anon` AND `authenticated` as SECURITY DEFINER.
  - `public.log_setting_value_change()` — executable by `anon` AND `authenticated` as SECURITY DEFINER.
  - `public.purge_expired_transcripts()` — executable by `anon` AND `authenticated` as SECURITY DEFINER.
  - `public.admin_get_user_sessions(uuid)` and `public.admin_list_users_activity()` — executable by `authenticated` (not `anon`) as SECURITY DEFINER; these two already have internal `role = 'admin'` gate checks confirmed by reading `20260803133500_admin_list_users_activity_per_category_costs.sql:44-48` (`if not exists (... role = 'admin') then raise exception 'forbidden'`), so they are not a live vulnerability, just flagged by the linter because Postgres GRANT doesn't know about the in-function check.
  - `compliance_check_transcripts` and `purge_expired_transcripts` are plausibly meant to be admin/cron-only utility functions with no obvious internal auth gate — **needs_api**: could not confirm their internal body logic without an additional `execute_sql` read of `pg_proc.prosrc`, which was out of scope for this pass. Flagging as the one item in this category that needs a follow-up check before treating it as resolved.
- **Remediation direction**: `REVOKE EXECUTE ... FROM anon, authenticated` on `compliance_check_transcripts`/`purge_expired_transcripts`/`log_setting_value_change` unless intentionally public, matching the project's own ADR history (PR #179's "missing REVOKE EXECUTE" incident, referenced in CLAUDE.md's `database-sentinel` integration note) — this is the same bug class that has hit this project before.

### M2. RLS enabled with zero policies on 7 tables

- **Verification method**: `get_advisors(type=security)`, `rls_enabled_no_policy` lint, 7 entries: `app_settings`, `contract_audit_runs`, `estimate_reconciliation_log`, `transcript_chapters`, `transcript_markers`, `transcripts`, `upstash_snapshots`.
- **Finding**: RLS is ON with no policy, meaning **zero rows are readable/writable via PostgREST for any role except `service_role`** (which bypasses RLS). Cross-checked table comments via `list_tables`: `app_settings` and `upstash_snapshots` have explicit comments stating this is intentional ("RLS-locked with no permissive policy -> only service_role... can access it"). `contract_audit_runs` has the same documented intent. `transcripts`/`transcript_markers`/`transcript_chapters`/`estimate_reconciliation_log` have no such comment confirming intent — **needs_api**: cannot confirm from schema alone whether these 4 are deliberately service-role-only (plausible, given `transcripts` is described elsewhere as ephemeral 72h storage accessed only by the worker) or an oversight. Recommend an explicit comment or policy be added to remove the ambiguity, not treating this as a hard confirmed bug.

### M3. Leaked password protection disabled

- **Verification method**: `get_advisors(type=security)`, `auth_leaked_password_protection` lint, live.
- **Finding**: Supabase Auth is not checking new passwords against HaveIBeenPwned. Straightforward config flip in Supabase Auth settings, no code change.

## 📋 LOW / INFORMATIONAL

### L1. `admin_list_users_activity`'s cost lateral has no explicit date bound (mitigated)

- **File**: `supabase/migrations/20260803133500_admin_list_users_activity_per_category_costs.sql:84-97`
- **Finding**: The lateral subquery aggregating `total_cost_usd`/turns filters only on `usage_logs.action IN (...)`, with no `created_at >=` bound, so query cost scales with however large `usage_logs` gets.
- **Verification method**: Read the migration file directly (shown above, lines 84-97 have no `created_at` predicate). Then checked whether this is actually unbounded in practice: `SELECT jobname, schedule, command, active FROM cron.job` (live) returned an active daily job `purge-usage-logs-daily` — `delete from public.usage_logs where created_at < now() - interval '30 days'` — running at `0 0 * * *`. So the table is capped at ~30 days of data by an independent, currently-active mechanism; this is a soft dependency (if the cron job is ever disabled or fails silently, this query's cost grows unbounded with no compensating control), not a live performance problem today (204 live rows).
- **Recommendation**: add an explicit `AND usage_logs.created_at >= now() - interval '30 days'` to the lateral so the query's cost bound doesn't silently depend on an out-of-band cron job staying healthy.

### L2. `vector` extension installed in `public` schema

- **Verification method**: `get_advisors(type=security)`, `extension_in_public` lint, live.
- **Finding**: Cosmetic/best-practice issue per Supabase's own linter — recommends moving `vector` out of `public`. Low urgency, used by `analyses.embedding` (1536-dim vector column, confirmed via `list_tables`).
