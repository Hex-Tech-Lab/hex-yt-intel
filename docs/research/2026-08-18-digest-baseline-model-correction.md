# Correction: Report A's "Haiku 4.5 baseline" premise was wrong (2026-08-18)

## Summary

Report A (`docs/research/2026-08-17-digest-regeneration-fidelity-test.md`, dated 2026-08-18 in its own title) claimed to test `openai/gpt-oss-120b` against "real Haiku-4.5 `executive_digest` baselines" on 6 historical rows, scoring content fidelity 69.5/100 mean. This premise is **incorrect**.

## Evidence

Queried the live `analyses` table via the Supabase Management API (`SUPABASE_ACCESS_TOKEN`, project `adnmbikaqnxivalqoild`) for the exact 6 row IDs Report A used, reading `executive_digest->>'model'` (the real column shape: `executive_digest` is JSONB with a top-level `model` field, set in `web/lib/usecases/GenerateExecutiveDigestUseCase.ts` line 128 from `completion.model`, not a separate column).

| Row ID (short) | `executive_digest.model` |
|---|---|
| `c866f529` | `openai/gpt-oss-120b` |
| `b35c77f7` | `openai/gpt-oss-120b` |
| `e076b945` | `openai/gpt-oss-120b` |
| `8af9413b` | `openai/gpt-oss-120b` |
| `35878592` | `openai/gpt-oss-120b` |
| `75870431` | `openai/gpt-oss-120b` |

All 6 "baseline" rows Report A selected were themselves generated by `openai/gpt-oss-120b`, not Claude Haiku 4.5. None are Haiku.

This is consistent with Report B's independent finding (`docs/research/2026-08-18-3tier-pipeline-fidelity-test.md`): all of ITS 5 sampled rows also show `executive_digest.model = "openai/gpt-oss-120b"`, and both `web/app/api/analyses/digest/route.ts` and `web/app/api/webhooks/digest/route.ts` call `resolveChatCascade()`, whose primary entry in `web/lib/config/cascade.ts` is `openai/gpt-oss-120b` — production digest generation is not Haiku-4.5-based today. There is no evidence of a historical Haiku-era row surviving in the current 9-row eligible set that Report A drew from; the table apparently does not currently contain any genuine Haiku-4.5-generated `executive_digest` row matching Report A's filter (`dimension_count=11 AND executive_digest IS NOT NULL AND analysis_markdown IS NOT NULL`).

## What this means for Report A's findings

Report A's headline claim — "GPT-OSS-120B scores 69.5/100 content fidelity vs. a real Haiku 4.5 baseline" — is **not a GPT-OSS-vs-Haiku comparison**. It was actually a **GPT-OSS-120B-vs-GPT-OSS-120B comparison**, where the "candidate" run used a possibly-different `max_tokens` budget/prompt path than whatever originally produced the row's stored `executive_digest`. The token-budget footgun (Tangent #1: `finish_reason: "length"` at `max_tokens=1200`) and the per-row fidelity variance (28–92) may still be real signal about GPT-OSS-120B's own run-to-run consistency and prompt/token sensitivity, but they say nothing about how GPT-OSS-120B compares to Haiku 4.5 — there is no confirmed Haiku baseline in this dataset to compare against.

## Root cause

Report A's row-selection step (its own Contract step 2) says it "Selected all 6 most-recent `Claude Haiku 4.5`-generated rows" but did not verify this against the real `executive_digest.model` field before running the test — it appears to have relied on an assumption (possibly from stale documentation, e.g. the pre-2026-07 state of ADR 003/011 model routing) rather than checking the live data, which is exactly the verification step this correction now performs.

## Independent cross-check attempted: OpenRouter generation logs

Per a coordinator request, attempted to verify the DB field against OpenRouter's own account-level activity logs as a second, DB-independent source of truth (`OPENROUTER_MANAGEMENT_KEY` from `.env.local`, confirmed present, not printed).

**Findings on what the API actually exposes**:
- `GET /api/v1/generation?id=...` returns per-generation detail, but only for a generation ID returned at call time by that same API key — there is no way to look one up by timestamp; not useful for auditing historical rows whose generation IDs were never captured/stored.
- `GET /api/v1/activity` requires a management key (a non-management key gets `403 Only management keys can fetch activity for an account` — confirmed live) and returns **daily-aggregated** usage grouped by `(date, model, provider endpoint)` — total requests/tokens/cost per model per day, not individual request records, and never contains request/response payload content.
- The endpoint enforces a **rolling 30-day retention window** (`"Date must be within the last 30 (completed) UTC days"`, confirmed live as of today). Report A's 6 target dates are 2026-07-09, 07-10, 07-14 (×2), 07-18 (×2) — three of those four distinct dates fall outside the current 30-day window and returned this error; only 2026-07-18 was queryable.
- On 2026-07-18 (the one in-window date), the account's aggregated activity shows **both** `anthropic/claude-haiku-4.5` (three separate provider endpoints, 45 combined requests that day) **and** `openai/gpt-oss-120b` (13 requests) were called that day — expected, since this is a shared multi-tenant account handling live production traffic across many features simultaneously, not a per-row log. Daily aggregation across all endpoints/features cannot attribute a specific `analyses` row's digest generation to one model call among dozens made that day.

**Conclusion**: OpenRouter's API does not expose historical generation logs queryable by timestamp with request-level attribution — confirmed by testing the real endpoints against the real key rather than assumed. It cannot serve as independent ground truth for which model generated a specific row's `executive_digest`, both because of the 30-day retention gap (covers only 1 of 6 target dates) and because even in-window data is daily-aggregated across the whole account, not per-request. This is a real, verified limitation, not an assumption.

**Falls back to the DB-field cross-check already performed above**, which remains the strongest available evidence: the `executive_digest.model` field is written directly by `GenerateExecutiveDigestUseCase.ts:128` from `completion.model` (the literal string OpenRouter's own completion response reports back at generation time) at the moment each digest is created — it is not a separately-maintained or backfilled label, so it is not independently "mislabeled or stale" in the way a denormalized cache field might be. Combined with the code-path evidence (both digest routes call `resolveChatCascade()`, whose primary is `openai/gpt-oss-120b`, per Report B) and the unanimous 6/6 result across Report A's own rows, the finding stands: all 6 baseline rows are GPT-OSS-120B, none are Haiku 4.5.
