## 2. Real production bugs found and fixed this session (all in PR #306 unless noted)

1. **Billing at 8/11 instead of 100%** — the headline finding. Two real production rows were billed `'completed'` at 8/11 dimensions before this fix.
2. **`validation_passed` DB column misreporting partials as `'completed'`** in the customer's History list (`SupabaseAnalysisAdapter.getUserHistory`'s status mapper ORs `billing_status==='completed'` with `!!validation_passed` — the latter was schema-validity-only, not completeness-gated). Confirmed live on 3 more production rows. Fixed in both `analysis-reaper.ts` and the main `persist/route.ts`.
3. **Detached/unawaited retry race** in `useSSEStream.ts` (PR #305) — self-caught via writing a real regression test, not found by review. The original "fix" looked correct on read but wasn't.
4. **A separate, still-partially-unexplained live data-loss bug**: analysis `6d9b61f2` (video `NE-62S4OYCg`, 2026-09-10) showed the client log claiming "5/5 streams completed" while the server has **zero** `analysis_chunks` rows and zero dimensions. Root cause narrowed to a hypothesis (worker's `atomicPersist` `hasContent()` guard checking a `finalText` accumulator that's fed by the identical `onDelta` calls as the model's own internal accumulator, so simple divergence is ruled out — the remaining candidate is an un-located non-streaming fallback path inside `LLMCascade` that could populate `result.finalText` without ever calling `onDelta`). **Not fixed, not fully diagnosed** — blocked on Cloudflare Worker logs, which this session's Cloudflare Observability MCP tool could not retrieve (confirmed genuine tool bug: its response-schema parser rejects the real API's shape, reproduced on both `events` and `invocations` views, not a permissions issue). **Next session: either get logs a different way (Cloudflare dashboard directly, or wrangler CLI `tail`), or keep investigating `LLMCascade.ts`'s non-streaming paths in code.**
5. **`"Invalid appUrl callback destination"`** (surfaced by OC's checklist audit finding a newer TestSprite report) — investigated and **resolved as NOT a production bug**: `worker/src/middleware/cors.ts`'s `isValidAppUrl` deliberately rejects `localhost` as a callback origin when the worker considers itself production (SSRF/open-redirect protection). TestSprite's Aug 20 run tested `localhost:3000` against the real deployed production worker, not a local instance — correctly rejected. Real users always hit an allowlisted production origin. This is a TestSprite test-infrastructure gap (can't exercise the full flow run this way), not a customer-facing defect.
