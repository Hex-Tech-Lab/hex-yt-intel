## Wave A — Chat Grounding Unification ("iron it out once and for all")

The chat's grounding universe for a video = **analysis + transcript + description +
metadata (video & channel)**, fetched and verified as one unit, not four independent
optional lookups that can silently disagree. Chat should also proactively confirm what
it *does* have ("yes, I have the transcript") rather than only ever refusing.

### A1. ✅ Analysis markdown/description read-path fixed
- **RCA**: Synthesis Console (`/api/analyses/[id]`) reconstructs markdown from
  `analysis_payload` when the `analysis_markdown` column is stale/empty. Chat's
  `getAnalysisGrounding()` read **only** the raw column, didn't even `select`
  `analysis_payload` — so an analysis rendering perfectly in the Console could ground
  chat as empty. Same shape for `description` (only read from `validation_report`,
  never from `analysis_payload.metadata.description`).
- **Fix**: `getAnalysisGrounding()` now applies the same reconstruction fallback + a
  payload-metadata description fallback. Commit `4f8b4228`.
- **Verified live** (this session): description now returns correctly, including
  affiliate links/chapter info from the video description ("do you have the
  description?" → full structured answer). **This half is confirmed working.**

### A2. ✅ Transcript returned "not included" — root cause traced and fixed
- **RCA (code-traced through the Worker repo)**: The `transcripts` table is only
  populated by `SupabaseTranscriptAdapter.upsertTranscript()`, called from
  `web/app/api/analyses/persist/route.ts` — **only when the request body's
  `segments` array is non-empty**. `segments` came from the Worker's
  `PersistService.persist({ segments: req.segments })`, which is the ORIGINAL
  inbound `StreamRequest.segments` — a field the browser never populates (Vercel
  deliberately blanks the transcript before minting the stream token per ADR-005;
  the real transcript is only ever fetched worker-side).
  - `worker/src/routes/analysis.ts`'s `fetchTranscriptIfMissing()` calls
    `TranscriptExtractor.fetch()`, which **already produces real timed segments**
    internally (`fetchFromPageHTML`/`fetchWithDecodo` both return
    `{transcript, segments}`) — but the function signature only returned the flat
    `transcript` string, discarding `result.segments` entirely. The persist call
    then fell back to the near-always-empty `req.segments`.
  - **Net effect confirmed**: `transcripts` table almost never got a row. Chat was
    telling the truth ("no transcript") on analyses that structurally had one.
- **Fix** (commits `0bec667e`, `0f791087`):
  - `fetchTranscriptIfMissing()` now returns `{transcript, segments}`.
  - Redis cache round-trip (72h TTL) now JSON-encodes `{transcript, segments}`
    instead of a flat string, with a defensive fallback for pre-fix plain-string
    cache entries — so a cache HIT on a repeat analysis doesn't regress back to
    segment-less (this closes a second leak: the 8×-analyzed video in the roster
    would have hit cache on repeats 2–8 and lost segments every time even if
    attempt 1 had them).
  - `buildStreamResponse()` threads resolved segments through a shared mutable
    (`resolvedSegments`, same pattern as existing `finalText`/`modelUsed`) so both
    the normal-completion and timeout/interrupted persist paths use real segments
    once resolved.
- **Verified so far**: worker `typecheck`, `build`, and `qa-intel` diff scan all
  clean (0 critical, 0 high — one empty-catch high finding surfaced and fixed
  immediately, commit `0f791087`). CI/CD Pipeline + Deploy Worker green on push
  (see verification checklist below for live confirmation still needed).
- **Not yet verified live**: needs a *fresh* analysis (not a cache hit on an
  already-broken cached entry) tested in chat — ask "do you have the transcript?"
  and "what happened at minute X?" Note: analyses created *before* this fix have
  no transcript row and won't retroactively gain one; only re-analyzed or newly
  analyzed videos will show the fix.
- **This was also the actual blocker for Wave B** (time-seek) — segments now
  exist to seek against; Wave B's remaining work is purely the frontend
  `TimestampLink` wiring (still orphaned, not touched by this fix).

### A3. ✅ "11/11 dims marked Partial" — root cause found and fixed (SQL, not app code)
- **RCA**: `get_user_history_overview()` (the Postgres function backing the history
  list) computed status via `case when billing_status = 'completed' ... then 'complete'`
  — but `'completed'` **is not a valid `billing_status` value** anywhere in the app
  (type is `'pending' | 'chargeable' | 'charged' | 'failed'`). The branch could never
  match. Every analysis, including fully-complete 11/11-dimension ones with
  `billing_status='chargeable'`, fell through to the `>=8 dims → 'partial'` branch.
  This is a **different bug** from the "auxiliary elements missing" scoping question
  (A4 below) — it's a dead SQL condition, full stop.
- **Fix**: new migration `20260722000000_history_overview_function_v4.sql`, matches
  `billing_status in ('chargeable', 'charged')` — same values `/api/analyses/check`
  and `/api/analyses/[id]` already use. Commit `b6c7c4ae`, pushed to `main`.
- **Verified**: **Not yet** — per ADR-013 CI auto-applies migrations on merge to
  `main` with no manual gate; needs confirmation the migration actually ran
  (check `supabase migration list` or re-test history list post-deploy) and that
  previously-mislabeled 11/11 analyses now show "Complete."

### A5. 🟡 Comments as a 5th grounding data stream — confirmed in scope, not started
- **User's ask**: add raw video comments as a 5th input to chat grounding (alongside
  analysis/transcript/description/metadata) as a "midway" step — available to chat

  which stays in Wave D).
- **My read, confirmed with user**: this is reasonable to decouple — raw comments in
  the grounding string is a much smaller lift than the full analysis-integration in

  infrastructure** (no scraper, no `comments` table/column — confirmed via repo

  scraper itself is shared, one-time work that serves both A5 (raw grounding) and
  Wave D (full analysis) — building it once unlocks both, so doing it now under A5
  isn't wasted if Wave D happens later.
- **Not started**. Needs: (1) scraper (YouTube Data API or equivalent, worker-side
  likely, matching the existing ingestion pattern), (2) storage (new column/table),
  (3) wiring into the grounding-assembly string in `ProcessChatMessageUseCase.ts`
  alongside transcript/description.
