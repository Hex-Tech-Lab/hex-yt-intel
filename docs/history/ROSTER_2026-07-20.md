## Wave A — Chat Grounding Unification ("iron it out once and for all")

The chat's grounding universe for a video = **analysis + transcript + description +
metadata (video & channel)**, fetched and verified as one unit, not four independent
optional lookups that can silently disagree. Chat should also proactively confirm what
it *does* have ("yes, I have the transcript") rather than only ever refusing.

### A1. ✅ Analysis markdown/description read-path fixed
- **RCA**: Synthesis Console (`/api/analyses/[id]`) reconstructs markdown from
  `analysis_payload` when the `analysis_markdown` column is stale/empty. Chat's
  `getAnalysisGrounding()` read **only** the raw column, didn't even `select`
  `analysis_payload` — so an analysis rendering perfectly in the Console could ground
  chat as empty. Same shape for `description` (only read from `validation_report`,
  never from `analysis_payload.metadata.description`).
- **Fix**: `getAnalysisGrounding()` now applies the same reconstruction fallback + a
  payload-metadata description fallback. Commit `4f8b4228`.
- **Verified live** (this session): description now returns correctly, including
  affiliate links/chapter info from the video description ("do you have the
  description?" → full structured answer). **This half is confirmed working.**

### A2. ✅ Transcript returned "not included" — root cause traced and fixed
- **RCA (code-traced through the Worker repo)**: The `transcripts` table is only
  populated by `SupabaseTranscriptAdapter.upsertTranscript()`, called from
  `web/app/api/analyses/persist/route.ts` — **only when the request body's
  `segments` array is non-empty**. `segments` came from the Worker's
  `PersistService.persist({ segments: req.segments })`, which is the ORIGINAL
  inbound `StreamRequest.segments` — a field the browser never populates (Vercel
  deliberately blanks the transcript before minting the stream token per ADR-005;
  the real transcript is only ever fetched worker-side).
  - `worker/src/routes/analysis.ts`'s `fetchTranscriptIfMissing()` calls
    `TranscriptExtractor.fetch()`, which **already produces real timed segments**
    internally (`fetchFromPageHTML`/`fetchWithDecodo` both return
    `{transcript, segments}`) — but the function signature only returned the flat
    `transcript` string, discarding `result.segments` entirely. The persist call
    then fell back to the near-always-empty `req.segments`.
  - **Net effect confirmed**: `transcripts` table almost never got a row. Chat was
    telling the truth ("no transcript") on analyses that structurally had one.
- **Fix** (commits `0bec667e`, `0f791087`):
  - `fetchTranscriptIfMissing()` now returns `{transcript, segments}`.
  - Redis cache round-trip (72h TTL) now JSON-encodes `{transcript, segments}`
    instead of a flat string, with a defensive fallback for pre-fix plain-string
    cache entries — so a cache HIT on a repeat analysis doesn't regress back to
    segment-less (this closes a second leak: the 8×-analyzed video in the roster
    would have hit cache on repeats 2–8 and lost segments every time even if
    attempt 1 had them).
  - `buildStreamResponse()` threads resolved segments through a shared mutable
    (`resolvedSegments`, same pattern as existing `finalText`/`modelUsed`) so both
    the normal-completion and timeout/interrupted persist paths use real segments
    once resolved.
- **Verified so far**: worker `typecheck`, `build`, and `qa-intel` diff scan all
  clean (0 critical, 0 high — one empty-catch high finding surfaced and fixed
  immediately, commit `0f791087`). CI/CD Pipeline + Deploy Worker green on push
  (see verification checklist below for live confirmation still needed).
- **Not yet verified live**: needs a *fresh* analysis (not a cache hit on an
  already-broken cached entry) tested in chat — ask "do you have the transcript?"
  and "what happened at minute X?" Note: analyses created *before* this fix have
  no transcript row and won't retroactively gain one; only re-analyzed or newly
  analyzed videos will show the fix.
- **This was also the actual blocker for Wave B** (time-seek) — segments now
  exist to seek against; Wave B's remaining work is purely the frontend
  `TimestampLink` wiring (still orphaned, not touched by this fix).

### A3. ✅ "11/11 dims marked Partial" — root cause found and fixed (SQL, not app code)
- **RCA**: `get_user_history_overview()` (the Postgres function backing the history
  list) computed status via `case when billing_status = 'completed' ... then 'complete'`
  — but `'completed'` **is not a valid `billing_status` value** anywhere in the app
  (type is `'pending' | 'chargeable' | 'charged' | 'failed'`). The branch could never
  match. Every analysis, including fully-complete 11/11-dimension ones with
  `billing_status='chargeable'`, fell through to the `>=8 dims → 'partial'` branch.
  This is a **different bug** from the "auxiliary elements missing" scoping question
  (A4 below) — it's a dead SQL condition, full stop.
- **Fix**: new migration `20260722000000_history_overview_function_v4.sql`, matches
  `billing_status in ('chargeable', 'charged')` — same values `/api/analyses/check`
  and `/api/analyses/[id]` already use. Commit `b6c7c4ae`, pushed to `main`.
- **Verified live (2026-07-22)**: confirmed by user. The first analysis completed
  *after* this fix deployed ("Best Free Shopify Themes (Top 8...)") correctly
  shows "Complete / 11/11 dims / Ready to view" in history — the SQL fix works
  for genuinely-complete new analyses.
- **New second bug found during verification** (see A6) — several *older* rows
  still show "Partial... 11/11 dims" simultaneously. Since the fixed SQL only
  shows "Complete" when `billing_status in ('chargeable','charged')`, this means
  those rows' `billing_status` is genuinely `'failed'` in the DB despite the
  markdown having all 11 dimensions — a real write-path bug, not a SQL bug.
  Tracked separately as A6, not a reopening of A3.

### A6. ✅ billing_status stuck 'failed' despite markdown having all 11 dimensions — root cause found and fixed
- **Symptom** (live test, 2026-07-22): multiple history rows show "Partial /
  11/11 dims / Incomplete" — e.g. "Best Shopify Themes for Beginners: Free vs
  Paid", "Best Shopify Themes - FREE vs PAID (2026 Review)", "10 Best Shopify
  Themes for Beauty and Cosmetics Stores", and the repeatedly-analyzed "Thmn
  El Horeya" (8×). All predate the A3 SQL fix's deploy, but A3 only fixed how
  the *existing* `billing_status` value is interpreted — it can't fix a row
  whose `billing_status` was incorrectly written as `'failed'` in the first
  place.
- **RCA, confirmed by tracing the actual code path (not the initial hypothesis
  above, which was wrong in mechanism)**:
  1. Each of the 5 parallel synthesis streams independently persists via the
     Worker's `buildStreamResponse` → `createAtomicPersist` (`worker/src/routes/analysis.ts`).
     That persist callback raced **every** persist call — including genuinely
     successful ones (`status: 'completed'`) — against a 15-second timeout. If
     the network round-trip to Vercel's `/api/analyses/persist` merely ran
     long (a persist-*write* timeout, not a generation timeout), the race
     fired a second persist call with status forced to `'interrupted'` —
     silently downgrading a real success.
  2. `web/app/api/analyses/persist/route.ts` only counts chunks with
     `status === 'completed'` toward `isFullyReceived`
     (`FINAL_CHUNK_STATUS` filter) — an `'interrupted'` chunk is **permanently
     excluded**, with no path back to `'completed'`.
  3. Once a later chunk-arrival re-triggers the 30-second chunk-reception-
     timeout check and finds that chunk still missing, `billing_status` gets
     written `'failed'` via `updateAnalysisResult`'s fallback logic (no
     explicit `billing_status` in that write path → falls through to
     `validationPassed ? 'chargeable' : 'failed'`).
  4. **Why bundles 4/5 specifically** (dimensions `[5,7,10]` and `[3,9,11]` —
     the exact ones missing in the earlier partial-analysis report): those are
     the two 3-dimension bundles. More content per request → larger persist
     payload → network round-trip statistically more likely to cross 15s.
- **Fix** (commit `446ce6ce`): the 15s-timeout-to-interrupted override now only
  applies when the request is already for an `'interrupted'` outcome (the
  client-disconnect/abort path, where a bounded best-effort attempt before
  giving up is correct). For `'completed'` requests, the code now awaits the
  real persist call directly — `PersistService` already retries the HTTP call
  internally (2 attempts, 10s `AbortSignal` timeout each), so the outer race
  added no protection for the success path, only harm.
- **Verified**: worker typecheck, build, and qa-intel diff scan (0 critical,
  0 high — one heuristic false-positive on the surrounding block, documented
  inline) all clean. Deploy Worker green on push.
- **Not yet verified live**: needs a **fresh** analysis with at least one
  slow/3-dimension bundle to confirm `billing_status` lands as `'chargeable'`
  when all 11 dimensions genuinely complete. Existing "Partial/11/11" rows
  predate this fix and won't self-heal retroactively — re-analyze to test.

### A7. ✅ Console/Sentry noise from stream JSON parsing, settings 406s, digest 409s — fixed
- **Symptom** (live test console dump, 2026-07-22): hundreds of
  `[Adapter] Unexpected error parsing raw sink for completion check` warnings
  during a single streaming analysis; two `user_settings` 406s; repeated
  `/api/analyses/digest` 409s; a `/monitoring` (Sentry tunnel) 429 mid-stream.
- **RCA**:
  1. `stream-delta-handler.ts` ran a completeness probe on every delta and only
     whitelisted one "expected" JSON.parse error message
     (`Unexpected end of JSON`) — but incomplete JSON mid-stream fails with many
     equally-expected shapes (`Unterminated string`, `Expected ',' or '}'`,
     etc.), so nearly every delta logged a false-positive warning. Volume of
     these is the likely driver of the observed Sentry-tunnel 429.
  2. `settings-adapter.ts`'s `fetchAdminSettings`/`fetchUserSettings` used
     `.single()`, which throws a `PGRST116` + HTTP 406 on the expected
     zero-rows case (already handled gracefully in JS, but noisy over the wire).
  3. `GenerateExecutiveDigestUseCase.ts` read `row.analysis_markdown` directly
     with **no fallback to `analysis_payload`** — the identical gap just fixed
     in `getAnalysisGrounding` (A2) for chat. Chunked persistence can populate
     `analysis_payload` before `analysis_markdown` catches up, so digest
     generation 409'd ("markdown is empty") on analyses that had real content.
- **Fix**: commit `9fbed72f`. (1) probe failures now silent by default, opt-in
  via existing `window.__CHAT_DEBUG`. (2) both settings lookups switched to
  `.maybeSingle()`. (3) digest use case now applies the same
  `reconstructMarkdown()` fallback as A2/the Console route; widened
  `DigestPersistencePort.verifyOwnership`'s return type to include
  `analysis_payload`.
- **Verified**: type-check, lint, qa-intel diff scan (0 critical/high) all
  clean. **Not yet live-tested** — needs a fresh analysis to confirm the
  digest 409 loop and warning spam are actually gone in the browser console.

### A9. ✅ Archived-suffix `video_id` leaking to client — root cause of a recurring "500 on history click" + fixed
- **Symptom** (live test console/network capture, 2026-07-22): repeated,
  vague "clicking in history produced error 500" reports across multiple
  turns, never with a specific failing request URL/status visible. This
  session's capture finally showed the real client-side error:
  `[YouTubePlayerAdapter] {message: 'Invalid video id', videoId:
  'vEC6e5dBi4Y_archived_1784392424.732239'}` immediately followed by
  `NotFoundError: Failed to execute 'insertBefore' on 'Node': ... not a
  child of this node` — a React DOM reconciliation crash from the player's
  failed mount attempt on the malformed id. This is what's being experienced
  as a hard error, not an actual HTTP 500 from any API route (both
  `/api/analyses/[id]` and its ownership-check dependency were already fully
  exception-hardened — confirmed by re-reading them, no gap found there).
- **RCA**: the reaper appends `_archived_<timestamp>` to `video_id` on
  superseded rows. The history-overview SQL function already strips this
  (`regexp_replace(video_id, '_archived_.*$', '')`) for the aggregated list
  view — but that stripping was **never applied** to (1) the per-analysis
  fetch (`/api/analyses/[id]/route.ts`, used by both AutoRestore and the
  history-click restore path) or (2) `getAnalysisGrounding`'s transcripts
  lookup (chat grounding) — both returned/queried the raw suffixed value.
- **Fix** (commits `6f6585d3`, `38e05106`): both call sites now strip the
  suffix before use — the API route before returning `videoId` to the
  client, the grounding adapter before querying the `transcripts` table by
  `video_id`. The transcripts-lookup fix is also a plausible contributor to
  the earlier-reported "chat inconsistently has/doesn't have the transcript
  for the same video" symptom, since an archived row would silently miss
  its own transcript on every grounding fetch.
- **Verified**: type-check, lint, qa-intel diff scan (0 critical, 0 high)
  clean on both commits. **Not yet live-tested** — needs a live click on a
  history row whose underlying video_id has been archived (i.e., re-analyzed
  since) to confirm the player mounts correctly and no DOM crash occurs.

### A10. ✅ Same DOM crash, different trigger — React reconciler crash on ANY YouTube playback error
- **Symptom** (live test, 2026-07-22, immediately after A9): pasting a
  video URL whose owner has embedding disabled (YouTube error 150 — a
  legitimate YouTube restriction, not a bug in this app) produced the exact
  same `NotFoundError: Failed to execute 'insertBefore' ...: not a child of
  this node` crash as A9, but for a completely clean video_id (no archived
  suffix). This proved the crash mechanism itself was broader than A9's
  specific trigger — **any** YouTube playback error could cause it, not just
  invalid/archived ids.
- **RCA**: `VideoPlayerCard.tsx`'s container `<div ref={containerRef}>` is
  owned by the YouTube IFrame API once mounted — it replaces the div's
  contents with a real `<iframe>`, invisible to React's virtual DOM. The two
  overlay banners (embed-restricted fallback, transient-error banner) were
  conditionally JSX-rendered as **siblings** before that div
  (`embedRestricted ? <A/> : playbackError ? <B/> : null`), so React had to
  insert/remove real DOM nodes around the container whenever the error state
  toggled — exactly when any playback error fires. Since the actual DOM
  under the container no longer matched React's fiber tree (the IFrame API
  had already mutated it), that insert operation threw.
- **Fix** (commit `7e6c884d`): both overlay slots now always render (stable
  DOM node count/order); visibility toggles purely via CSS
  (`hidden`/`flex` classes) instead of conditional JSX branching, so React
  never needs to insert/remove siblings around the third-party-mutated
  container, regardless of what triggered the playback error.
- **Verified**: type-check, lint, qa-intel diff scan (0 critical, 0 high)
  clean. **Not yet live-tested** — needs a video with embedding disabled (or
  any other YouTube playback error) to confirm the fallback UI now renders
  without crashing.

## A8. ✅ Word cloud showing dimension section titles as fake "entities" — fixed
- **Symptom** (live test, 2026-07-22): word cloud rendering "APEX INTELLIGENCE",
  "PROVENANCE, METADATA & VIRALITY PROFILE", "PSYCHOLOGICAL & RHETORICAL LAYER",
  "COMPARATIVE & QUANTITATIVE ANALYSIS" as if they were extracted entities.
- **RCA**: `useKnowledgeGraph.ts` has two tiers — (1) real fine-grained entity
  nodes from the worker's `knowledgeGraph` payload (dimension 8), and (2) a
  client-side TF-IDF fallback synthesizer (`KnowledgeGraphSynthesizer`,
  `web/lib/intelligence/knowledge-graph.ts`) that only runs when tier 1 is
  empty. The fallback builds **one node per dimension** with
  `label: d.name` — the literal ALL-CAPS section title.
  `WordCloud.tsx` tokenized `node.label` uniformly for every node regardless
  of source, so fallback nodes fed section-title fragments into the cloud.
  **Not a new regression in the word-cloud code** — the same fallback path
  firing far more often because more analyses are currently landing without
  a real knowledge graph, which is A6's exact symptom (dimension 8/bundle-2
  incompleteness). Fixing A6 should reduce how often this fallback fires at
  all, but the display-layer bug was real and independent.
- **Fix** (commit `b5f7995e`): `WordCloud.tsx` now prefers `node.keyTerms`
  (real per-dimension extracted terms, already computed by the synthesizer
  but previously unused for this purpose) over `node.label` whenever
  non-empty; `label` remains the fallback for real entity nodes where
  `keyTerms` is empty.
- **Verified**: type-check, lint, qa-intel diff scan (0 critical, 0 high) all
  clean. **Not yet live-tested** — needs a partial/fallback-graph analysis to
  confirm the word cloud now shows real terms instead of section-title

- **Open follow-up, not fixed this session**: `KnowledgeGraphCanvas`/
  `IntelligencePanel` still render `node.label` directly for the fallback's
  dimension-level nodes — that's a coarser but arguably legitimate view there

  prompt-documented *value-domain* contracts against the schema. Full RCA:
  `docs/history/RCA_2026-07-23_WHY_CONTRACT_AUDIT_MISSED_KG_SCALE_BUG.md`.
- **Fix** (commits `22397b2e`/`21bab85a`): schema bounds corrected to 1-10,
  matching what `KnowledgeGraphCanvas.tsx` already assumed (`node.weight / 10`
  normalization) — the schema was the sole outlier, not the rest of the system.
  One test fixture (`synthesis-stream-adapter.test.ts`) updated off its stale
  `weight: 0.8` assumption.
- **Verified**: re-validated the exact failing production payload against the
  fixed schema — now passes. Full vitest suite (843 tests) green. CI/CD green
